## 3. Raw-SQL fallbacks

**Application code (`src/`) has no `sql` template tag anywhere.**

1. **All migrations are hand-written SQL.** graphile-migrate is SQL-first and has no schema language.
   - M1 is `reference/schema.sql` almost verbatim, including the new partition `REVOKE`. The only change: `CREATE EXTENSION` was replaced with an assertion, because the superuser bootstrap creates the extension.
   - M2 (column, backfill, `BEFORE INSERT OR UPDATE` sync trigger) and M3 (drop trigger, belt-and-braces backfill, `SET NOT NULL`, drop column) are hand-written.
   - Nothing was generated by a tool.
2. **The `<=>` distance needs `$castTo<number>()`** (T3). It is not raw SQL; it is the builder's binary operator. Kysely types comparison operators as `SqlBool`, so the distance column needs a cast.
3. **`pgvector.toSql(vec)!`** (T3). halfvec is generated as `string`, so embeddings go in as pgvector's text form. `toSql` is typed `string | null`, so a non-null assertion is needed.
4. **`JSON.stringify` for every jsonb write** (`claim_version.object`). kysely-codegen types jsonb as `Json` for inserts. `pg` would send a bare JS string as-is, which is invalid JSON. The types accept `object: "v3"`, which then fails at runtime. This is a type hole, not raw SQL.
5. **Untyped access to partitions** (T1 partition test): `db as unknown as Kysely<Record<string, {tenant_id: string}>>`. kysely-codegen excludes partitions by default, so `claim_version_p0` has no type. The test uses the cast only to attempt the forbidden query.
6. **Test-only SQL.** None of this is used by application code.
   - `psql` via `docker exec` for catalog checks: T4 object inventory, T6 entity shape and `display_name` list, T8 pgTAP.
   - `pg_dump --schema-only` for dump comparisons.
   - One `pg` query in T7 to tamper with a recorded hash.
   - `CREATE/DROP DATABASE` in `src/migrate.ts`, because graphile-migrate does not create databases.
7. **`test/pgtap/rls.sql`** is hand-written pgTAP, as the task requires.

## 4. Surprises

**Reference schema: RLS did not cover the `claim_version` partitions. Now fixed in the reference schema.** RLS is enabled only on the partitioned parent. `GRANT ... ON ALL TABLES` gave `skal_app` SELECT on `claim_version_p0..p3`, and querying a partition directly does not apply the parent's policy.
- In the first run, a T1 `FINDING` test read B's claim versions through `claim_version_p*`. The pgTAP run reported 4 TODOs: `not ok 29 - RLS enabled on partition claim_version_p0 # TODO ...`, and the same for p1 to p3.
- `reference/schema.sql` now ends with `REVOKE ALL ON claim_version_p0, ..., claim_version_p3 FROM skal_app`, and M1 does the same.
- Now T1 asserts 42501 on each partition, and pgTAP has 4 passing `table_privs_are(..., 'skal_app', ARRAY[]::text[])` checks.
- Residual risk: any future partition (or `GRANT ... ON ALL TABLES` re-run) must repeat the REVOKE. The pgTAP check finds partitions from the catalog, so it would catch a new one.

**Changing a committed migration in graphile-migrate is manual.**
- `commit` marks committed files read-only (`EPERM` on write).
- `uncommit` only pulls back the latest migration, and only while `current.sql` is empty, so the tool offers no supported way to edit M1 under M2 and M3.
- What I did:
  1. cleared the read-only flag;
  2. appended the REVOKE to the M1 body;
  3. recomputed all three `--! Hash` / `--! Previous` headers with the tool's own `calculateHash(body, previous)`. I first checked that this method reproduced the old M1 hash (`sha1:4849ac1e…`).
  4. set the files read-only again.
- New hashes: M1 `sha1:ae794fcc…`, M2 `sha1:4742f941…`, M3 `sha1:baa1a407…`. M2 and M3 bodies are unchanged; their hashes change only because the chain does.
- Any database already migrated with the old chain would need resetting. Here every run recreates its databases.

**graphile-migrate does not re-verify the hashes of migrations already applied.** T7 sets `graphile_migrate.migrations.hash = 'sha1:tampered'` for `000003.sql`. A further `migrate` succeeds silently, and the fleet report shows `head: "sha1:tampered"`. The applied state is only as trustworthy as that table. To compare hundreds of databases, compare head hash plus row list (cheap and deterministic), and separately check each row against the committed file headers.

**Applied migrations are recorded by number, not by file name.** For example, `000003.sql` is recorded, not `000003-m3-contract-drop-name.sql`. Several expectations in my tests had to be corrected for this.

**`commit` validates against an empty shadow database, so data-dependent failures get through.** T6b's broken M2 adds `CHECK (display_name <> '')`. It is valid on an empty database and fails only on an existing row whose `name` is `''`.
- It got through because the hash was computed with the tool's own `calculateHash`, exactly as `commit` would compute it.
- At run time the whole migration rolled back, because each migration runs in its own transaction:
  - entity columns stayed `tenant_id,id,campaign_id,kind,name,custom`
  - no sync function and no sync trigger remained
  - `pg_dump` was identical
  - applied rows were still `["000001.sql"]`
- The fixed M2 then completed through M3, and `display_name` values were `,Ada`.

**graphile-migrate's internal pool calls `process.exit(1)` on a connection error.** Dropping a per-task database `WITH (FORCE)` in `afterAll` killed its still-pooled connections, and the Vitest worker died. The fix: per-task databases are not dropped at the end; each run recreates them.

**There is no "migrate to version N".** To hold a database at M1 or M2 (T5, T6, T7), I copy the first N committed files into a temporary folder (`prefixFolder`). It works because the hash chain only looks backwards.

**kysely-codegen and the expand/contract window.** Generated against the M2 database, `entity.name` and `display_name` are both nullable plain `string | null`, which is right for the database but wrong for either app version. Two overrides fix it (`scripts/codegen.ts --overrides`):
- `name: Generated<string>`: M2 code may omit it, and the trigger fills it.
- `display_name: ColumnType<string, string | undefined, string>`.

The approach that works:
- keep one generated types file per schema version (`types-m1.ts`, `types-m2.ts`, `types.ts`)
- compile each deployment against its own file
- keep M2-era code off `name`, so it survives M3

**After the pgTAP grant, codegen started emitting `tap` views.** I added `GRANT USAGE ON SCHEMA tap TO skal_migrator` to the bootstrap so T8b can run as the migrator. kysely-codegen then also generated `TapPgAllForeignKeys` and `TapTapFunky`, and `--verify` failed in the first clean run. Fix: `--include-pattern public.*`.

**squawk needs `--assume-in-transaction`.** Without it there are 46 findings, including "missing transaction" for files graphile-migrate already wraps in a transaction. With it there are 13 findings, all warnings, pinned as a snapshot:

The M3 findings are the real contract-step hazards. Good: the committed files are exactly the executed SQL, so linting them is linting the real thing. The headers are SQL comments.

**HNSW is not chosen with 40 rows.** The planner prefers a bitmap scan on `claim_current`, then a nested loop on `claim_embedding_pkey`, then a sort. With `enable_seqscan` and `enable_sort` set off locally (via `set_config` in the same transaction), the plan shows `Index Scan using claim_embedding_hnsw on claim_embedding e`. That proves the index can be used, not that it is chosen at this size.

**Windows network share (Z: is `\\10.42.1.10\...`).**
- pnpm needed `nodeLinker: hoisted`.
- pnpm runs scripts with a UNC cwd. cmd.exe refuses a UNC cwd, and Vitest workers crash on `file://10.42.1.10/...` module URLs.
- `shellEmulator: true` and scripts that call `node <entry>` directly fix the first problem but not the Vitest one.
- On the share I ran `node node_modules/vitest/vitest.mjs run` directly: 15/15 passed. The one-command check was done in a clean local copy.
- This is an environment issue, not a tool issue.

**Bootstrap addition.** `db/bootstrap-extensions.sql` adds `GRANT USAGE ON SCHEMA tap TO skal_migrator;` to the README's superuser bootstrap, so the migrator can run pgTAP.

## 5. `withTenant`

```ts
// src/db/index.ts
export function withTenant<Schema, T>(
  db: Kysely<Schema>,
  tenantId: string,
  fn: (tx: Transaction<Schema>) => Promise<T>,
): Promise<T> {
  return db.transaction().execute(async (tx) => {
    await tx
      .selectNoFrom((eb) =>
        eb.fn<string>("set_config", [eb.val("app.tenant_id"), eb.val(tenantId), eb.lit(true)]).as("ctx"),
      )
      .execute();
    return fn(tx);
  });
}
```

Usage: `withTenant(db, tenantId, (tx) => tx.selectFrom("entity").selectAll().execute())`. The whole callback runs in one transaction on one pooled connection. `is_local = true` scopes the setting to that transaction, which is why T2's interleaving cannot leak.
